# Authority, execution and release boundaries

The trusted owner interface holds an in-memory capability for the separate authority process. The model returns parsed JSON action proposals. It is never given the owner token, Drive mount credentials, an unrestricted Python interpreter, a shell, or a grant-minting tool. The action client exposes only checking and dispatch. HMAC grants bind goal version, tool set, resource prefix and expiry. Dispatch recomputes authority against the exact arguments, atomically reserves budget/idempotency, then records observed receipts. Changing scope, stopping, expiry and process restart invalidate earlier grants. Pending outcomes remain UNKNOWN until inspected.

The Python coordinator, notebook kernel, owner account and host OS are trusted. Separate Python processes alone do not protect against arbitrary malicious native code running as the same host user. The supported threat is malicious model/document proposals and generated Python submitted through the restricted executor, not an attacker already controlling the notebook kernel or the host. In particular, `approved=True` is an owner-side API; it is never an LLM tool.

Filesystem tools walk pinned directory handles using `openat`-style directory FDs and `O_NOFOLLOW`, reject traversal, links, unexpected file types and hard links, bound file sizes, use atomic writes, and retain recovery copies for explicit overwrites. A file hash can be supplied as a write precondition. There are no delete, network, account, payment or external-message tools. Generated code receives only copied input files.

Generated Python runs in a separate scratch process with Linux Landlock filesystem restrictions, a syscall allowlist through seccomp, no inherited credentials, no network/fork/exec/ptrace, and CPU/address-space/file/output/descriptor limits. On root Colab runtimes it first drops to the unprivileged `nobody` UID/GID. Syscalls that could mutate file metadata outside Landlock's coverage are excluded. Parent cancellation kills the worker process group. Standard-library imports are supported; arbitrary pip packages, native build tools and network access are intentionally unavailable in this sandbox. If kernel enforcement cannot be established, the action is BLOCKED; there is no unrestricted fallback. Kernel vulnerabilities and a full adversarial security audit remain outside this prototype's assurance.

World-model training uses consented observed records or explicitly labelled validated simulator transitions. Refused actions are not trained as environmental effects. Operation success is not automatically a goal-completion label. Memory deletion removes indexed records and their dependent claims/skills; it does not unlearn existing parameters or erase separate run journals/raw evidence. For complete private-state removal, the owner must also remove the associated `runs/` and `raw_evidence/` files, authority history and historical snapshots, and reset/retrain affected checkpoints. The owner can invoke `MemoryStore.delete`, `set_training_consent`, and `DrivePersistence.delete_snapshots(approved=True)`; these operations are not model tools.

Improvement candidates can change a fixed, bounded numeric planner configuration only. A separate trusted evaluator process receives that configuration as data and generates test labels outside the proposer. It uses no owner tokens or cloud credentials. Exact config/proposal/evaluator hashes, a preregistered gate, per-family results, and rollback are recorded. Promotion requires an owner action and a matching unchanged baseline. The evaluator's source and diagnostics are public; this is not a secret independent external audit or a secure platform for arbitrary candidate native code. Small-model candidate gates are internal retention diagnostics. Language-model LoRA remains disabled because its broader release gate is unperformed.

Drive snapshots use checksummed manifests, a final commit marker, SQLite online backups and an intact previous-snapshot fallback. Other writers must be idle during a snapshot. The acting loop saves after every three tool operations and at goal completion; training saves at checkpoint boundaries. Sudden runtime termination can lose later unsaved progress. Snapshots contain private user state and authority history and should remain private in the owner's Drive. The pretrained weight cache stays on ephemeral Colab disk and is redownloaded on a fresh runtime.

Behavioural tests cover forged approval, tampered/stale grants, revocation while code is running, scope and cumulative budgets, unsafe paths, symlink/hardlink conflicts, protected-host-file access, denied sockets/subprocesses/metadata mutation, checkpoint corruption and restoration. Passing these tests is bounded engineering evidence, not a proof of alignment or zero risk.
